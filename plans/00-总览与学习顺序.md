#00. 总览与学习顺序

这套 `plans/` 文档不是项目完成报告，也不是照抄上游 `nano-vllm` 的代码清单。

它的作用很简单：

>站在当前仓库的真实代码上，说明下一步该改什么、为什么要改、改完怎么验收。

读每一篇时，请一直分清三件事：

1. **当前仓库状态**：现在代码里已经有什么，还缺什么。
2. **本篇目标状态**：照着这一篇改完后，代码应该变成什么样。
3. **上游参考状态**：上游 `nano-vllm`、Hugging Face Qwen3，以及2026 年前后新出现的扩展仓库给我们的设计参考。

不要把这三件事混在一起。很多读起来绕的地方，都是因为“现在已经有的代码”和“未来要补的代码”混着说了。

---

##1. 当前仓库里已经有的东西

当前仓库主要是一个精简版 Python 推理原型，核心文件是：

- `config.py`
- `sampling_params.py`
- `llm.py`
- `example.py`
- `engine/`
- `layers/`
- `models/`
- `utils/`
- `tests/test_Day1.py` 到 `tests/test_Day4.py`

当前仓库还没有下面这些后续文件：

- `bench.py`
- `tests/test_Day5.py`
- `tests/test_Day6_tp.py`
- `tests/test_Day6_cudagraph.py`
- `tests/test_Day7.py`

写文档和改代码时要守住这个边界：

>未来要新增的文件，不能写成当前仓库已经存在的文件。

同样也要守住另一条边界：

> 社区里已经有人做出来的新特性，不能自动等价成“当前仓库现在就已经有这条执行路径”。

##2.参考谁

###2.1 第一参考：上游 nano-vllm

参考仓库：

```text
https://github.com/GeeeekExplorer/nano-vllm
```

上游可以告诉我们：

- PagedAttention 的主线怎么组织。
- Tensor Parallel 的线性层应该怎么切。
- CUDA Graph 的 capture / replay 边界应该放在哪里。
- `chunked prefill`、`prefix caching`、`torch.compile` 等能力通常会落在哪些模块。

但上游现在已经比本仓库更完整。不要直接把上游当前代码当成本仓库当前状态。

###2.2 第二参考：Hugging Face Qwen3

Qwen3 模型语义以 Hugging Face 为准，重点看：

- `configuration_qwen3.py`
- `modeling_qwen3.py`

它们主要回答：

- `num_attention_heads`、`num_key_value_heads`、`head_dim` 分别是什么意思。
- `q_norm`、`k_norm` 应该放在哪里。
- `rope_theta`、`rope_scaling` 怎么解释。
- Qwen3 Decoder Layer 的残差顺序应该怎么走。

###2.3 第三参考：2026 年前后的扩展型 nano-vllm 仓库

这一组不是“照搬对象”，而是“吸收方向”的参考来源。

最近最值得关注的扩展方向主要有：

- `chunked prefill`
- `radix / prefix-tree cache`
- `speculative decoding`
- `MoE inference`
- `FP8 / KV cache quantization`
- `GPU offload`
- `JAX / MLX / C++ / TTS` 等跨后端适配

这类仓库的价值，主要在于告诉我们：

1. 社区正在把哪些能力从“论文概念”变成“可运行实验”。
2. 某个新特性最自然的接入边界在哪里。
3. 哪些能力适合直接接进当前主线，哪些更适合先写成独立实验原型。

##3. 为什么不能直接照搬上游或社区扩展仓

原因很直接：

1. 上游是完整工程，本仓库是教学复刻版。
2. 上游已经包含 TP、CUDA Graph、benchmark，以及一些更完整的调度细节，本仓库还在逐步补。
3. 社区扩展仓往往只验证单一特性，不一定和当前仓库的接口边界完全兼容。
4. 本仓库很多脚本必须先能单卡直接跑。
5. 当前代码已经有自己的类名和接口，比如 `Sequence`、`Scheduler`、`ModelRunner`。

所以每篇文档都要用这个顺序讲：

1. 当前代码是什么样。
2. 本篇只改哪些地方。
3. 哪些参考只是设计启发，哪些才是当前仓库可以直接落地的修改。
4. 改完用什么命令验收。

##4. 推荐学习顺序

这套文档分成两段：

1. **主线00~07**：先把当前仓库的单卡主线、TP、CUDA Graph 和 benchmark 学扎实。
2. **进阶08以后**：再吸收2026 年前后 nano-vllm生态里最值得学的新特性，例如 chunked prefill、radix prefix cache、speculative decoding、MoE、FP8、GPU offload 和跨后端实现。

先把主线跑通，再进阶。不要一开始就跳到 speculative decoding 或 MoE。

- `MoE inference`

这些特性已经明显超出“Day1 到 Day7 的基础复现线”。

##5. 每篇开始前先做什么

不要一上来就复制代码块。先确认当前文件长什么样。

建议每篇开始前都做这几步：

```bash
#进入项目根目录
cd nano_vll_repro

# 快速确认当前文件是否存在
ls config.py sampling_params.py llm.py
ls engine layers models utils tests

# 看当前测试入口
ls tests
```

如果要改某个具体文件，先读它：

```bash
#例子：准备改 Linear之前，先看当前实现
sed -n '1,260p' layers/linear.py

#例子：准备改调度器之前，先看当前实现
sed -n '1,260p' engine/scheduler.py
```

这样做是为了避免一个常见错误：

> 文档里以为某个类还没有，实际代码里已经有了；或者文档里以为某个接口存在，实际代码里根本不是这个签名。

如果你准备读08以后这些进阶实验篇，建议再多做一步：

```bash
#先重新看一遍当前调度、KV Cache 和 Context 边界
sed -n '1,260p' engine/block_manager.py
sed -n '1,260p' engine/scheduler.py
sed -n '1,320p' engine/model_runner.py
sed -n '1,220p' utils/context.py
```

原因很简单：

>进阶特性大多不是“平地起楼”，而是在已有 `BlockManager / Scheduler / ModelRunner / Context` 边界上继续演化。

##8. 最后要学会什么

这套文档的目标不是让你机械抄代码。

真正要学会的是：

1. 一个请求从 `LLM.generate()` 到 `Sequence`，再到 `Scheduler`、`ModelRunner`、`Attention`，最后生成 token，是怎么流动的。
2. KV Cache 为什么要按 block 管。
3. `weight_loader` 为什么要挂到参数对象上。
4. 模型主干、logits计算、sampler 为什么要拆开。
5. TP 和 CUDA Graph 应该接在哪些边界上。
6. `chunked prefill` 为什么本质上是在改调度而不是改单个 kernel。
7. `radix prefix cache` 为什么是对“前缀复用数据结构”的升级，而不是简单 hash 表替换。
8. `speculative decoding` 为什么会同时影响模型执行、接受/拒绝逻辑和调度语义。
9. 为什么 MoE、FP8、GPU offload这些能力不能只靠“补一个文件”就讲清楚，而必须明确结构边界和实验边界。

先从 `01` 开始。如果你对 PagedAttention 主线不清楚，读完 `02` 后先读 `02A`。如果你已经把 `00~07` 跑通，再继续读 `08`以后。
